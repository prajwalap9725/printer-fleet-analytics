EXECUTIVE SUMMARY

Web-deployed medical machine-learning demonstrations usually stop at a trained model, an explanation plot and a form. This project implements and measures a complete screening system, MedBuddy.ML, for two diseases: heart disease (Cleveland, 1,025 rows) and diabetes (Pima Indians, 768 rows). A benchmark suite trains six classifiers per disease inside identical leakage-safe pipelines, selects the winner by held-out evidence (Logistic Regression, ROC-AUC 0.9250 for heart disease; XGBoost, ROC-AUC 0.8424 for diabetes) and saves everything the serving API needs as a single artifact. A FastAPI backend serves predictions, and a Streamlit frontend renders them with patient-level SHAP attributions.
The project then adds three trust layers served in the same prediction payload. A Mondrian class-conditional split-conformal layer calibrates on a leakage-safe validation split and reports a prediction set with a &gt;=90% coverage target; when the set is ambiguous the system abstains and routes the case to a clinician-review state (measured empirical coverage 0.936 and 0.940 on untouched test data). An actionable counterfactual service computes the minimal, clinically feasible feature changes that would flip the decision, respecting immutable attributes such as age and sex. A subgroup fairness audit reports error rates by sex and age group at the deployed threshold, including a measured false-negative rate of approximately 0.44 for under-40 patients on the diabetes data.
All of this is locked behind an automated test suite covering the API contract, calibration integrity, counterfactual achievability and fairness computation. The repository trains, serves, explains, abstains, audits and tests itself, and every number in this report is reproducible from the included commands.

CHAPTER 1INTRODUCTION
1.1 Objective
The primary objective of this project is to implement an end-to-end clinical screening system for two diseases - heart disease and diabetes - in which the deployed artifact, not a notebook prototype, is the object of study. The system must train a family of candidate models under identical preprocessing, select the winner by held-out evidence, and serve selected predictions through a documented HTTP API with a web interface on top of it.
A second objective is to make the deployment trustworthy rather than merely accurate. Three trust layers are implemented and measured: a Mondrian class-conditional split-conformal layer that attaches a certified prediction set to every prediction and abstains to a clinician-review state when the set is ambiguous; an actionable counterfactual service that returns the minimal, clinically feasible changes needed to flip the decision; and a subgroup fairness audit that reports error rates by sex and age group at the actual deployed threshold.
A third objective is honesty about calibration. The decision threshold used in production is not the sklearn default of 0.5; it is a Youden-J threshold tuned on a separate validation split and never tuned on test data, and the data splits are constructed to prevent the duplicate patient rows in the heart data from appearing in both train and test. The completeness objective of the survey - leakage-safe splitting, per-model SHAP explanation, and a locked automated test suite - turns these practices into artefacts that can be inspected rather than claimed.
1.2 Motivation
Screening models for heart disease and diabetes are abundant in the literature and in open-source repositories. What is rare is a system that reports how confident it is in each individual prediction, and that is honest about which kinds of patients its errors fall on. A model that achieves good average accuracy can still be dangerous in a screening context if it confidently assigns 'healthy' to a patient who is not; the false negative is the error medicine cannot afford, while a false alarm is recoverable by follow-up testing. This asymmetry motivates the recall-first metric policy and the calibrated operating threshold used throughout the project.
The uncertainty motivation is more demanding than aggregate metrics. Probabilities from boosted trees and linear models are frequently miscalibrated, and a single probability offers no statement about how much data supports it. Conformal prediction provides a distribution-free answer: the manipulated set Ŝ(x) contains the true label with a guaranteed probability, so a wide or two-class set is an honest 'I am not sure' and can trigger a different clinical path. prior work applies this on the same datasets in research form, which motivates rather than discourages integration into a runnable app.
The fairness motivation is equally concrete: deployed clinical tools often are not audited, and published surveys report that most cardiac machine-learning papers do not even emphasise the facility to show error disparities by sex. A screening tool that works differently for under-40 patients than for older ones bears scrutiny, and the project therefore audits the exact threshold that is deployed rather than a tuning-run threshold.
The software-engineering motivation is to turn these ideas into an inspectable pipeline. Explicit Pydantic request schema (validation at the boundary), a single settings module, a strict test suite and reproducible commands mean every claim in this report can be re-executed from the repository rather than taken on trust.
1.3 Background
The Cleveland heart-disease dataset combines thirteen clinical attributes - age, sex, chest pain type, resting blood pressure, cholesterol, fasting blood sugar, resting ECG, maximum heart rate, exercise-induced angina, ST depression, slope, number of major vessels and thalassemia - with a binary disease label. The University-of-California Irvine distribution used here contains 1,025 rows, of which many are duplicates; the duplication motivates the leakage-safe splitting described in Chapter 3 rather than a change to the data.
The Pima Indians diabetes dataset contains 768 female patients over 21 with eight attributes: pregnancies, glucose, blood pressure, skin thickness, insulin, body mass index, diabetes pedigree function and age. Physiologically, zero blood pressure or zero insulin is impossible, so those zeros are codes for missing data; the pipeline converts them to NaN and lets a median imputer fitted on training rows alone fill them.
A model zoo spanning linear, kernel, tree, boosted-tree and neural families is compared because no single family dominates on 13-feature tabular medical data. SHAP (Shapley Additive exPlanations) assigns each feature a signed contribution to a single prediction; the expander of choice is selected per winning family (TreeExplainer for tree models, LinearExplainer for logistic regression, KernelExplainer as fallback) so attributions remain exact where possible.
Conformal prediction constructs prediction sets whose coverage is guaranteed by exchangeability alone. The Mondrian (class-conditional) variant calibrates a separate nonconformity quantile per class, which is robust to class imbalance: at level  - the project uses = 0.10, targeting 90% coverage, the returned set satisfies P(y ∈ Š(x)) ≥ 1 − α for each class.
Counterfactual explanations answer a different question from SHAP: not 'which features pushed this risk up' but 'what would have to change for the decision to change'. Wachter and colleagues introduced the optimisation view; Ustun and co-workers framed it as actionable recourse; DiCE industrialised it as a library. The constraint regime here (immutable demographic attributes, permitted physiological ranges, whole-step changes for discrete clinical codes) follows the clinical literature so that returned changes are something a patient could actually do.
1.4 Scope and boundaries
The implemented scope begins with the two CSV datasets and ends with the served prediction payload (prediction, probability, SHAP contributions, conformal set, counterfactual), the fairness audit endpoint, the Streamlit interface and the benchmark report. Everything between them - splitting, preprocessing, training, calibration, artifact serialisation and the test suite - is part of the deliverable.
The project does not implement cryptographic secure aggregation, federated training, model-retraining online, multi-tenant persistence, a production deployment pipeline or a prospective clinical trial. It does not claim diagnostic authority: the conformal layer qualifies orders, not certainties, and the intended use is decision support for a clinician. Longitudinal outcome studies, survival modelling and integration with hospital record systems are outside the review-2 scope and listed as future work.
CHAPTER 2PROJECT DESCRIPTION AND GOALS
MedBuddy.ML is, before anything else, a system with two independently valid disease pipelines behind one HTTP contract. A request specifies the disease and a complete set of clinical features; the response carries the predicted class, the calibrated probability, the SHAP attribution list, the conformal prediction set with its certainty verdict, and a verified counterfactual - all computed by the deployed artifact for this patient. A separate endpoint returns the subgroup fairness audit, and a third serves the full benchmark report. The architecture is deliberately single-process and container-ready: one FastAPI application, one Streamlit frontend, two joblib artifacts, one SQLite-free deployment.

3.2 Resource requirements and measurement limits

CHAPTER 4DESIGN APPROACH AND DETAILS
4.1 System architecture
The architecture separates training from serving with one shared configuration module. A single pydantic-settings object is imported by the training entrypoint, the API and the frontend, so a path or a port exists in exactly one place. The benchmark suite (src/training/evaluate.py) builds each candidate as a sklearn Pipeline, runs it against both diseases, computes metrics at two operating points (default 0.5 and the calibrated threshold), emits figures, and serialises the winner plus preprocessing plus explainer background into one joblib artifact per disease. The backend then loads that artifact lazily on first request and keeps it resident (single process-global registry), so the served model is exactly the artifact the benchmark selected.
4.2 Leakage-safe data handling and threshold calibration
Two data-quality facts drive the design. First, the heart CSV contains 723 duplicated feature rows; a naive random split would place copies of the same patient in both train and test, inflating test metrics. The suite therefore groups rows by a signature hash of all feature columns and holds entire groups out of the test set (GroupShuffleSplit, seed 42). Second, the Pima data encodes missing values as zero; the pipeline converts the physiologically impossible zeros to NaN and lets a median imputer fitted on training rows alone fill them, so no test statistic ever leaks into preprocessing.
The operating threshold is tuned by Youden's J (sensitivity + specificity − 1) on the validation split only, and both the tuned value and the calibration provenance are serialised into the artifact and shown in every API response (calibrated_threshold). Test data is never touched during tuning, which keeps the reported test recall honest; for heart disease the calibrated threshold of 0.377 yields a test recall of 0.931 - four missed positives of 72 - compared with 0.897 at the default 0.5.
4.3 Trust layer N1: Mondrian conformal certified-risk inference
The conformal layer implements Mondrian (class-conditional) split-conformal prediction. For each disease the untouched validation split provides calibration nonconformity scores; per class, the (1 − α) quantile with the finite-sample correction rank = ceil((n + 1)(1 − α)) is precomputed and cached. At request time, any class whose probability falls within its class quantile belongs to the prediction set. The verdict logic is deliberately conservative: a single-class set earns a 'certified' verdict, and a two-class set earns an abstention with an explicit message that clinician review is recommended.
This design buys insensitivity to the base model's probability calibration, because class-conditional quantiles track each class' score distribution separately. Measured on untouched test data, empirical set coverage is 0.936 for heart disease and 0.940 for diabetes against the 0.90 guarantee at α = 0.10. The measured abstention behaviour is deliberately conservative; the project treats uncertainty as a routing signal to a human rather than as an error to be suppressed. The report wording is careful to state that conformal guarantees prediction-set coverage - and not per-patient certainty or improved clinical outcomes - which is the qualification used in the accompanying research paper.
4.4 Trust layer N2: actionable counterfactual what-ifs
The counterfactual service (src/backend/services/counterfactual.py) searches the feature space of the deployed pipeline, not of a surrogate. Age and sex are immutable. Continuous physiological attributes may only move within their permitted clinical ranges. Discrete clinical codes (chest pain type, slope, ca, thal) may only change in whole steps. The objective combines the change needed to push the probability past the decision threshold (with a margin) with a normalised L1 distance penalty, so the returned counterfactual is the smallest change, not merely a change. Every candidate move is re-scored by the deployed artifact to verify the flip actually happens; if no clinically permissible combination flips the decision, the payload returns achievable = false with the closest documented state.
Because the counterfactual is computed inside the same HTTP payload as conformal and SHAP data, the frontend can render a single coherent card: the badge answers 'how sure', the SHAP breakdown answers 'why', and the counterfactual answers 'what would change it' - all three about the same patient, computed by the same pipeline version.
4.5 Trust layer N3: subgroup fairness auditing
The fairness service (src/backend/services/fairness.py) computes group-level confusion matrices and derived rates by sex and by age band, strictly at the deployed threshold and strictly on the untouched test split. The endpoint GET /api/fairness/{disease} returns the group table together with the disparity summary. The most consequential recorded finding is on the Pima data: the false-negative rate for patients under 40 is approximately 0.44 - missed disease in nearly one of two young positives - which is the kind of error average accuracy hides. The audit exists as live code rather than as a one-off notebook so that every deployed model can be audited without new engineering. 7.5 Discussion
Three findings organise the discussion. First, the per-disease winner differs, and the difference is instructive rather than accidental: the leakage-safe heart split rewards the regularised linear model while the imbalanced Pima data rewards gradient boosting, so a fixed ('always use XGBoost') policy would have been wrong in one of the two pipelines. Second, the trust layers change the operational reading of the numbers: 0.931 recall is meaningful only against a threshold chosen without test leakage, and the abstention rate is an operational signal, not noise. Third, the fairness audit shows that the deployed system's errors are not distributed evenly, and the audit is only honest because it runs at the deployed threshold on the untouched split - at any other operating point the reported disparity would be an artefact of a threshold nobody serves.
CHAPTER 8SUMMARY
This project implements MedBuddy.ML, a runnable, benchmark-driven, trust-aware clinical screening system for heart disease and diabetes, and measures each layer of it against the artifact it actually serves.
8.1 Completed work and technical contribution
The completed implementation covers leakage-safe dataset engineering (GroupShuffleSplit for 723 duplicated heart rows; zero-to-NaN median imputation for Pima), a six-model zoo benchmark per disease with two operating points and evidence-based winner selection (Logistic Regression, ROC-AUC 0.9250, heart; XGBoost, ROC-AUC 0.8424, diabetes), a FastAPI serving layer with strict clinical validation and a single-payload trust contract (prediction, probability, SHAP, conformal set, counterfactual), and a Streamlit interface rendering certified-vs-abstain badges, two-sided SHAP breakdowns and counterfactual cards.
The technical contribution lies in the integration: the conformal layer calibrates per class on a leakage-safe split and abstains to a clinician-review state (measured coverage 0.936 and 0.940 at α = 0.10); the counterfactual layer searches the feature space of the deployed pipeline under clinical mutability constraints and verifies every returned flip; the fairness layer audits the exact served threshold on the untouched split. No component is claimed as a new invention in isolation; the contribution is that they are combined, measured and locked behind tests in one runnable system.
8.2 Results and objective achievement
Every objective in Table 2.1 has observable evidence behind it: per-model benchmark records, endpoint behaviour, measured conformal coverage, test-verified counterfactual flips, subgroup audit rows and a 12-test suite that passes from a clean environment. The research-grade claims are qualified in line with the conformal and counterfactual literature: 'certified' refers to prediction-set coverage, abstention is a routing recommendation rather than an outcome improvement, and the counterfactual guarantee is achievability by the deployed pipeline, not a causal promise.
8.3 Limitations
The conformal calibration currently reuses the validation split that also tunes the Youden-J threshold, a documented tuning-bias consideration; measured coverage stays above the guarantee at these split sizes, but the clean fix is a dedicated calibration split. The datasets are small and historical, and neither carries labels suited to outcome studies, so no claim of clinical benefit is made. Concurrency and deployment-scale behaviour are unmeasured. The fairness audit is restricted to the two axes present in the data (sex and age); no intersectional or socioeconomic analysis is possible from these columns.
8.4 Future enhancements
The next research step is a dedicated conformal calibration split and a coverage-monitoring job that re-measures coverage as new data arrives. A prospective study comparing outcomes for abstained versus certified predictions would close the loop between the routing signal and clinical value. Third-party public data (with traceable provenance) would strengthen the fairness audit to more subgroups. An authenticated multi-user deployment, container orchestration outside a laptop and continuous benchmark regression on dependency upgrades complete the engineering roadmap.
